# Threat Model v0

**Status:** M0 foundation; incomplete and non-production.

## Assets

AssureCTL is intended to protect the integrity of:

- repository, base revision, head revision, and change-set subject binding;
- verification contract identity and acceptance criteria;
- effective policy identity, source provenance, and precedence;
- evidence producer and execution provenance;
- evidence artifact integrity and freshness;
- findings, waiver authorization, verification verdict, completion decision, and receipt contents.

## Adversaries

The design considers:

- a change-producing agent that benefits from being marked complete;
- a malicious or careless contributor able to edit candidate code and repository files;
- a compromised or misconfigured CI workflow;
- a process that forges evidence metadata or replays old evidence;
- an integration that publishes a misleading status under an unpinned identity.

## Primary trust boundary

The worker proposing or producing a change must not be the authority that marks the change complete. Agent prose, status files, self-generated keys, and self-authored `passed` assertions are untrusted by default.

## M0 protections

M0 provides only foundational protections:

- closed enum values for authority, evidence, outcome, finding category, verdict, waiver status, and decision;
- fail-closed handling of malformed requirement and finding inputs;
- explicit precedence where indeterminate verification or a blocking finding blocks completion;
- preservation of a known failed verdict when a separate blocking finding exists;
- waiver semantics that preserve a failed technical verdict;
- receipt constraints requiring an authoritative protocol baseline and layer-compatible trusted policy provenance;
- trusted-base policy sources bind symbolically to the receipt subject's exact base revision instead of repeating a candidate-controlled revision value;
- deterministic, side-effect-free decision evaluation;
- no network fetch, arbitrary command execution, custom cryptography, or authoritative receipt claim.

## Deferred protections

Later milestones must implement and test:

- canonical repository identity and exact Git subject resolution;
- trusted-base and organization policy retrieval and resolution;
- trusted verification-contract authority;
- evidence path safety, digest validation, freshness, and replay rules;
- CI/OIDC producer identity and protected workflow provenance;
- source-pinned GitHub App required checks;
- semantic enforcement that every trusted-base marker resolves to the receipt subject's actual base object;
- cross-array matching between failed requirements and exact waiver targets;
- in-toto/DSSE/Sigstore-aligned signing and verification;
- issuer rotation, revocation, retention, and audit search;
- time-of-check/time-of-use protections.

## Explicit non-goals

AssureCTL does not prove that code is bug-free, universally correct, secure, fit for purpose, or production-ready. It does not determine whether human requirements are complete or wise.

## Residual risk

A deterministic evaluator can faithfully apply an inadequate policy or contract. A trusted producer can still run weak tests. Protected identities can be compromised. Therefore receipts must identify their exact subject, inputs, policy, contract, verifier, and claim boundary rather than imply universal assurance.
