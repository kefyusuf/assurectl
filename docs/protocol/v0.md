# Protocol v0 Overview

**Status:** unstable design draft; advisory only.

Protocol v0 maps the AssureCTL domain vocabulary to reviewable JSON artifacts. It exists to constrain implementation discussions before M1 loaders and validators are introduced.

## Artifact map

| Concept | Artifact |
|---|---|
| Project policy | `schemas/policy.v0.schema.json` |
| Work unit and acceptance criteria | `schemas/verification-contract.v0.schema.json` |
| Produced observation and provenance metadata | `schemas/evidence-envelope.v0.schema.json` |
| Evaluation record | `schemas/receipt.v0.schema.json` |

## Semantic separation

The protocol preserves these independent values:

```text
evidence state      VALID | INVALID | MISSING | STALE | UNTRUSTED
observed outcome    PASSED | FAILED | ERROR
technical verdict   PASSED | FAILED | INDETERMINATE
waiver status       NOT_APPLICABLE | VALID | INVALID
completion decision APPROVED | REJECTED | BLOCKED | ACCEPTED_WITH_RISK
```

A valid evidence envelope can report a failed outcome. A valid waiver can permit `ACCEPTED_WITH_RISK`, but the technical verdict remains `FAILED`. Missing, stale, invalid, and untrusted required evidence are indeterminate and block completion.

Receipt verdict/decision pairs are constrained to:

- `PASSED/APPROVED`;
- `INDETERMINATE/BLOCKED`;
- `FAILED/BLOCKED` when a known failure coexists with an indeterminate required verification;
- `FAILED/REJECTED`;
- `FAILED/ACCEPTED_WITH_RISK`.

## Receipt completeness and auditability

A receipt must contain at least one requirement result. An empty result set cannot be represented as `PASSED/APPROVED`.

Findings carry a stable code and one typed category:

```text
SUBJECT | CONTRACT | POLICY | EVIDENCE | VERIFICATION |
WAIVER | AUTHORITY | PROTOCOL | INTERNAL
```

The receipt embeds every supplied waiver record needed to audit risk acceptance. Each record identifies its exact requirement or finding target, repository and work-unit scope, optional head revision, reason, accepted risk, approver identity and externally resolved authority, issue and expiry timestamps, validity status, and normalized-input digest. The digest is not a signature or trust root. `NOT_APPLICABLE` remains a per-requirement status and is not a waiver-record status.

## Subject binding

The planned receipt subject records repository URI, exact base and head Git object IDs, the versioned change-set algorithm, and its digest. Pull request numbers and branch names may be adapter metadata but are not immutable subject identity.

## Trust statements

- Integrity metadata is not producer provenance.
- A producer cannot establish its own authority merely by declaring an identity.
- Local example identities and artifacts are advisory and not merge-grade.
- Authoritative policy and contract sources are deferred to later milestones.
- A receipt records every policy layer used to derive the effective policy, including each source digest, resolved trust status, authority basis, and source revision when applicable.
- An approver-authority value in a receipt records verifier resolution; a waiver payload cannot promote its own approver authority.
- No v0 file proves code correctness, security, bug freedom, or production readiness.

## Implementation boundary

M0 tests JSON syntax, root schema metadata, selected cross-field invariants, and the consistency of the included example artifact digest. Full JSON Schema validation, path safety, revision validation, producer trust, freshness, waiver authorization, and receipt construction are M1 or later work.

Timestamp `format` annotations are not treated as sufficient validation. Schema patterns provide a lexical RFC3339 prefilter. Ingestion must parse timestamps, reject impossible dates, enforce `finished_at >= started_at`, and require waiver expiry to be later than its issue time.

## Authority resolution

Policy, contract, evidence, and waiver payloads do not declare their own trust level. Authority is resolved by the loader or integration from external context. A receipt may record the resolved trust decision, but input files cannot promote themselves by setting an authority field.
